# 直播快速取名与详细取名需求稿

状态：供用户审阅，尚未作为开发验收基线确认。

日期：2026-10-30

修订：R2，同步设计评审修正。新增运行要求属于本轮文档修订；限流、窗口和模拟数值为工程试验值，不冒充实测业务数据。

项目：jinyu

本文整理本轮讨论中的需求。已确认的产品方向与建议方案分别标明；未确定的数值不作为已承诺效果。本文不代表功能已经实现，不覆盖原有 PRD，不修改现有代码。

## 1. 背景与问题

应用主要在抖音直播中使用。主播根据观众评论取名，需要操作简单、出结果快、名字能够讲出文化依据，同时不能反复推荐少量名字。

当前直播取名依赖模型现场生成候选、寓意和出处，再进行检查和展示。模型配置已由用户选择，本轮不以更换模型为优化方向。

本轮曾使用现有探测脚本，以王姓、男孩、双字名调用实际 Provider，返回六个候选耗时约 40.2 秒。这是单次 Provider 观测，可能包含内部重试，不代表端到端平均耗时。

之前出现过以“现代常用字组合”“成词义”充当出处的问题。用户明确要求名字有具体古典书籍出处，不能用模糊词义说明替代。

仅建立 100～200 个名字的小库无法证明长期直播够用。固定排序还可能让少数名字反复出现。需要同时解决资料质量、姓氏匹配、库容量和近期重复控制。

## 2. 已确认的产品方向

| 项目 | 已确认需求 |
| --- | --- |
| 服务划分 | 直播快速取名、特殊要求详细取名两条路径 |
| 快速模式输入 | 姓氏、性别，不收生日、时辰、辈分字、避讳等其他要求 |
| 快速模式来源 | 提前准备的精选名字库 |
| 选择方式 | 系统自动筛选，主播不手动翻库或逐个选名 |
| 已知性别 | 首推一个、备选两个 |
| 性别未知 | 男向、女向各三个，共六个，不能重复凑数 |
| 拼音 | 每个展示名字都有完整姓名拼音 |
| 文化依据 | 名字具有具体古典书籍出处 |
| 风格 | 不提供预设风格，不默认套用“端庄”“清雅”等风格要求 |
| 特殊需求 | 观众联系主播，收集具体要求后由模型深入分析取名 |
| 详细取名交付 | 沿用现有完整报告和图片 |

快速模式默认双字名；需要单字名等要求时转入详细取名。快速模式是否支持单字切换，不作为本版新增功能。

## 3. 目标与不做的事

### 3.1 目标

- 主播填写姓氏、选择性别后即可得到推荐。
- 快速取名及换一组不等待现场模型调用。
- 推荐名字具有真实出处和可直接展示的解释。
- 系统按完整姓名检查搭配，自动挑选首推和备选。
- 控制同一轮、同姓近期和同场直播中的重复。
- 名字资料和筛选结果可以保存、回看、导出图片。
- 特殊要求继续由详细取名处理，不挤进快速表单。

### 3.2 不做的事

- 不承诺绝不重名、每个名字独创或终身不重复。
- 不用“100 分”“最佳命运”等说法包装内部排序。
- 不要求主播在直播中审核整个候选库。
- 不因本次需求改造名字分析功能、账号体系或直播视觉主题。
- 不新增支付、CRM、自动私信、群运营或联系方式管理系统。
- 不为快速模式建设在线多模型评审、向量数据库等复杂基础设施；是否需要索引由实际数据量决定。

## 4. 用户流程

### 4.1 快速取名

1. 主播输入姓氏，选择男孩、女孩或未知。
2. 服务启动预热完成后，系统检查输入并使用已加载的名字资料；未就绪时页面明确提示准备中，不让首次点击承担全量历史扫描。
3. 按性别方向取候选，组合完整姓名。
4. 排除不合格候选，结合近期使用记录排序。
5. 自动组成三个名字，未知性别则组成两组各三个。
6. 展示完整姓名、拼音、寓意和出处信息。
7. 主播讲解，可保存图片、换一组或进入下一位观众。

快速模式不得读取上一位观众残留的生辰、辈分或避讳信息。输入只有姓氏和性别，不意味着已考虑其他家庭要求。

### 4.2 换一组

- 保留当前姓氏和性别。
- 排除当前这一轮已展示过的名字，重新自动筛选。
- 一轮指从本次首次取名开始，到主播明确进入“下一位”为止。
- 若不能组成完整的新一组，明确告知没有足够的新候选，不重复填充，不暗中调用模型。
- 新一组失败时保留上一组有效结果，便于主播继续讲解或存图。

### 4.3 详细取名

1. 观众有特殊要求时联系主播。
2. 主播收集实际需要的信息。
3. 使用现有详细取名能力调用模型。
4. 检查名字是否满足要求、拼音和出处是否可靠。
5. 通过现有完整报告和图片交付。

引导文案建议：

> 直播快速取名：留下姓氏和男孩／女孩。\
> 有辈分字、避讳或生辰等要求，可联系主播详细取名。

## 5. 快速表单与输入约定

| 字段 | 要求 |
| --- | --- |
| 姓氏 | 必填，沿用现有一至两个汉字的支持范围，包含复姓 |
| 性别 | 男孩、女孩、未知；未知是一种有效选择 |
| 名字字数 | 快速模式固定双字，不另加表单项 |
| 其他字段 | 快速模式不展示、不使用 |

- 非法输入在筛选前拦截，说明具体原因。
- 多音姓氏要按姓氏读音处理，不直接套日常读法。
- 无法确定姓氏读音时，在输入框旁提示核对或转详细取名，保留输入及上一份结果，不消费候选、不自动重试。已有可靠读音的常见多音姓正常取名并提示核对，不能一律报错。
- 不为了快速表单新增账号、档案或观众身份登记步骤。

## 6. 精选名字库

### 6.1 名字库与古籍库的区别

古籍库保存原文，能用于核对引文；精选名字库保存经过检查、可以用于推荐的名字及解释。古籍中存在某两个字，不代表组合后适合起名。

项目已经具备本地古籍语料和引文核验能力，可以作为起点，但不能把现有全部诗句直接当成已审核的名字。

### 6.2 来源与准备流程

建议优先使用项目现有《诗经》《楚辞》《论语》及唐诗宋词等可核对语料。

准备流程：古籍原文 → 程序或模型提出候选 → 自动核验 → 内容审核 → 正式可用名字库。

- 模型批量提出候选发生在直播之外。
- 自动检查负责原句匹配、重复、字数、已知不合适用字等。
- 内容审核负责原文语境、字义解释、名字是否自然等不能仅靠字符串匹配确认的内容。
- 不将模型自行声称“已核验”当作核验记录。
- 使用外部整理数据或代码前确认来源及许可；不直接复制商业产品的收费解读。
- 审核由谁执行、投入多少工作量，需在准备正式库前明确。不能默认由主播在直播过程中承担。

### 6.3 每条名字必须具备的内容

以下是资料要求，不是已经决定的数据库字段名称。

| 内容 | 说明 |
| --- | --- |
| 稳定标识 | 便于去重、使用记录和修正 |
| 名字用字 | 不含姓，快速模式为两个字 |
| 适用方向 | 男向、女向或适用于两边；属于使用建议，不是客观性别定律 |
| 读音资料 | 名字用字的已确认读音，完整姓名仍需结合姓氏处理 |
| 寓意简解 | 适合直播直接讲的一小段解释 |
| 取名解释 | 两个字的关系，以及与原句的联系 |
| 来源信息 | 书名、篇名、原句；诗词有明确作者时可保留作者 |
| 取字依据 | 标明直接取词、句内取字等具体关系 |
| 必要提醒 | 容易误读、误写等确实存在的问题，没有则不编写 |
| 可用依据 | 是否已完成入库检查，不能把待检查资料当正式资料使用 |

可用资料须足以直接展示和存图，不能在用户点击存图后才补调模型写内容。

### 6.4 入库质量要求

- 书名、篇名、原句能够对应，允许明确记录版本或简繁差异，不随意改写引文。
- 名字与引文有明确关系，不拿无关真诗句装饰名字。
- 区分原句含义和现代取名寄意，不能把延伸解释冒充古文原意。
- 阅读必要的上下文，不能只凭摘出的漂亮词语决定适合取名。
- 避免生硬拼凑、明显不良寓意和已知过度热门组合。
- 不仅因为一个字热门就淘汰所有包含它的名字。
- 不仅因为同声调、同结构就判断名字不合格。
- 同一名字可能有多个出处，但不能作为多个独立名字增加可用数量。
- 不强制填满读音、字形评价；有实际信息才写，不补通用套话。

### 6.5 规模与扩充

正式规模暂不固定为 200、1000 或其他数字。100～200 个仅可作为流程验证样本，不能作为正式直播够用的结论。

正式容量按下列指标确定：

- 指定姓氏筛选后，男向、女向各有多少可用名字。
- 同一姓氏在不重复的情况下能换多少组。
- 模拟一场直播的候选不足次数和名字重复频率。
- 同组用字是否集中、是否过多依赖少数诗句。

举例：100 次取名中，80 次性别明确、20 次未知，会产生 80×3＋20×6＝360 个展示位置。这是容量估算示例，不是已确认的直播量，也不等于必须有 360 个互不重复的名字。

按测试结果补充不足的方向，不为凑数量降低入库标准。长期使用需要持续补充和纠错，但本版不要求先建设复杂的名字库后台。

### 6.6 紧急停用

正式库完整更新可以在停播后发布；直播中发现明确问题时，维护者可以不重启地停用某个名字或某个完整姓名。下一次新推荐应用有效停用信息，格式错误保留上次有效版本并提醒维护者。

已提交报告与图片快照不自动改写；当前结果若涉及已停用名字，应提示主播换组。停用功能与增加新名字的审核发布流程分开，不允许通过紧急文件绕过审核加入新名字。

## 7. 自动筛选与推荐规则

### 7.1 必须满足

- 只使用已通过入库检查的资料。
- 名字字数符合快速模式约定。
- 满足所选性别方向；中性名字可供两边考虑，但未知结果中只能出现一次。
- 排除维护名单中明确禁止的完整名字组合。
- 检查姓氏与名字组合后已知的明显问题。
- 同次结果无重复，未知性别的六个名字也无重复。
- 排除当前取名这一轮已经展示过的名字。
- 所有最终推荐均有出处和完整拼音，不用缺失资料的名字凑数。

### 7.2 排序和组名建议

在满足基本要求的候选中，依次参考同姓近期次数、同场次数、已知热门用字数量，再在同等条件下轮换。删除不可计算的“使用风险较少”排序；明确的不良搭配由过滤处理，其他注意事项据实展示。

- 明确禁用的名字组合与特定姓氏组合分别过滤，不将模糊风险词句转成分数。
- 同姓近期未推荐过的优先。
- 同场直播使用较少的优先。
- 同等条件下轮换选择，避免固定前三名长期霸榜。
- 同组尽量减少相同字和高度相似含义，但不得为多样性加入不合格名字。
- 随机或轮换只发生在合格候选之间，不用随机抽古诗字代替精选。
- 首推是当前条件下的推荐顺序，不向观众展示虚假的客观质量分数。

### 7.3 防重复范围

| 范围 | 处理 |
| --- | --- |
| 同一结果 | 必须去重 |
| 本轮换一组 | 不重复本轮已展示的名字；耗尽后提示 |
| 同姓近期 | 优先不重复，具体时间或次数窗口待测试确定 |
| 同场不同姓氏 | 对近期使用过的名字降低优先级，不永久禁止 |
| 跨日期、跨家庭 | 允许合理复用，不承诺永久唯一 |

统计范围明确为已提交的快速推荐。详细模型取名报告不计入快速模式同姓近期、同场和本轮排除；不承诺跨模式防重复。私下生成详细报告不等于直播展示过它。

同一结果被再次查看、保存图片或幂等重放，不算一次新推荐。正式快照提交前失败不消费候选；快照已经提交但响应断线时仍算一次，重试返回原结果，不再消费。

“同场直播”通过服务端确认的“新一场”操作定义，刷新保留当前场次，旧标签页不能自行复活已结束场次。本版不接入抖音开播状态。近期计数按时间裁剪，结束场次释放其活跃计数；幂等缓存淘汰后仍能从快照恢复同一请求结果，不能因清理内存重新推荐。

### 7.4 能力边界

- 自动谐音检查只能识别已有词表与规则覆盖的问题，不保证覆盖全部方言或昵称联想。
- 热门名单应记录依据和适用范围；区域、历史榜单不能冒充实时全国重名数据。
- 快速模式没有收集家庭避讳，不能宣称已避开亲属姓名。
- 不给候选不足设置暗中降低出处要求或禁用规则的兜底。

## 8. 直播结果与图片

### 8.1 性别明确

直播展示首推一个、备选两个。三个名字都有完整拼音和可查看的真实出处。

首推重点呈现名字、寓意、取名依据；两个备选给出简短寓意。信息长度要适合手机直播阅读，不强制展示无价值的读写段落。

保存图延续已讨论的结构：首推详解、两个备选简解，三个名字都有完整拼音与出处。

### 8.2 性别未知

- 清晰区分男向推荐、女向推荐，每组各三个。
- 六个名字都有完整拼音、寓意和出处资料。
- 男向、女向两组不重复。
- 快速未知性别结果不展示跨性别的全局首推。直播、报告页、名字标签、两种图片入口与历史都按两组表达，不能让内部兼容字段误导用户。
- 保存交付必须覆盖六个名字，不能丢失另一组。
- 图片采用一张分组长图，还是男女各一张，尚待用户确认；不得默认为现有三名图片已经满足要求。

### 8.3 保存与历史

- 保存的是当次选出的名字和解释快照，重新打开不能重新随机选择。
- 库中内容以后更新，不应无提示改写已交付报告。
- 结果显示与图片来自同一份资料，避免名字、拼音、出处不一致。
- 快速结果应能与模型详细取名结果区分，不能把库内推荐冒充已经结合生辰的定制结果。
- 新路径兼容已有报告；旧数据不能自动获得“已审核古籍出处”等新的可信标记。

## 9. 详细取名

### 9.1 收集信息

由主播根据实际需求收集姓氏、性别、字数、辈分字和位置、避讳字，以及其他明确要求。需要生辰参考时，再收集出生日期和时辰。

- 沿用现有公历输入约定，确认观众提供的日期类型；不能默默把农历当公历。
- 出生时刻不确定时保留不确定性说明，不伪装成精确结论。
- 不重新引入预设风格；允许表达具体要求，例如避开某个字、希望便于读写。

### 9.2 生成与交付

- 模型依据已收集条件深入分析和生成候选。
- 检查字数、辈分位置、避讳等硬性条件。
- 检查出处、拼音、原文与解释的关系。
- 没有可靠出处的候选不能用模糊文案冒充符合要求。
- 本次必须修正详细生成路径：先核验出处，再计算合格数量；不足时有限补充并重新检查，仍不足则明确失败，不能留空出处当成功。报告与图片复用不意味着保留此处旧缺陷。
- 生辰内容仅在用户要求且资料足够时出现，不作命运或效果保证。
- 沿用现有完整报告和图片，不新增另一套详细交付系统。
- 现有详细生成的候选数量、失败恢复等行为，除与本需求直接冲突的部分外，本轮不扩大修改。

## 10. 异常与反馈

| 场景 | 期望行为 |
| --- | --- |
| 姓氏为空或不合法 | 提交前提示，不开始筛选 |
| 男向或女向候选不足 | 说明不足的方向，不重复、不混组凑数 |
| 换一组耗尽 | 保留上一组，提示暂无更多新候选 |
| 资料缺失或不可用 | 排除该候选；不足时明确提示 |
| 无法确认读音 | 给出核对提示，不能生成假拼音 |
| 保存失败 | 保留当前结果，允许重试保存，不重新取名 |
| 重复点击 | 不产生互相覆盖的结果或重复记录 |
| 服务准备中或失败 | 禁用新取名，显示准备状态或失败原因；不让用户点击后等待全量重建 |
| 请求频率超限 | 提示稍后重试，保留当前结果，不自动反复提交 |
| 紧急停用文件异常 | 保留上次有效名单，向维护者提示；首次无有效版本不进入就绪态 |

快速模式候选不足时可以引导联系主播详细取名，但不自动切到耗时模型生成。

### 10.1 最小运行保障

- 账号级提交频率限制和同时进行数量限制，不能靠换轮次ID绕过；同一已提交请求的重试不算新推荐。
- 主播操作区显示就绪状态、当前姓氏各方向可用量及本轮剩余量，容量少时提醒；不遮挡观众所看的名字。
- 区分名字库筛选后不足、本轮换组剩余不足和近期重复多，不能混称全局池耗尽。
- 记录候选不足率、读音未确认次数、限流次数及耗时，统计显示样本量；服务器耗时不能冒充端到端展示耗时。
- 仅使用轻量状态和可轮转日志，不建设独立运维平台。

## 11. 性能与验收

### 11.1 建议的性能目标，尚待实测确认

- 本机服务就绪后，从提交到全部姓名与拼音可读，P95 不超过 2 秒；就绪后的首次点击也纳入，不选择性排除慢样本。
- 换一组采用同一测量口径。
- 该目标包括结果展示需要的接口和处理时间，不能只测筛选函数。
- 启动预热、首次加载、字体或图片加载与就绪后连续使用分别记录。预热必须发生在可取名之前，其耗时仍单独披露。
- 快速模式的取名、换组、普通存图不调用 LLM。

2 秒是建议验收目标，不是现有系统实测成绩。实际测试环境、样本数及冷启动要求在开发前确定。

### 11.2 功能验收清单

| 编号 | 场景 | 合格标准 |
| --- | --- | --- |
| A01 | 只填姓氏和男孩 | 返回首推一个、备选两个，无其他必填项 |
| A02 | 只填姓氏和女孩 | 返回三个符合方向的名字 |
| A03 | 选择未知 | 男向女向各三个，共六个互不重复的名字 |

A14 先使用下节固定试验负载；正式观众分布和可接受重复率待实测决定，不能只跑一个姓氏就宣称正式库够用。A21 纳入本次整体交付，不能以快速模块通过替代。

### 11.2.1 开工前固定的试验负载

基线为120分钟100位观众，男40、女40、未知20；其中30位各换一次，男12、女12、未知6，共130次新推荐、468个名字位置。随机种子为20261030。连续模拟七个每日场次后观察第八场和时间窗口边界。

为立即形成可运行夹具，先用明确标注为合成的非均匀姓氏分布：王18%、李16%、张14%、刘12%、陈10%、杨8%、赵7%、黄6%、周5%、吴4%。不称其为人口普查数据。正式容量验收前必须额外冻结一份有来源、年份及人数或占比的公开姓氏分布，或匿名实际直播分布；只有排名不能当概率。

另测同姓集中、全部未知、频繁换组、复姓和多音姓以及连点场景。容量模拟不能通过限流拒绝请求来伪装通过。具体夹具与指标定义见设计稿 §6.6。

试验运行默认值：同姓近期七天、单场最长12小时、账号每滚动分钟30个新请求、同时一个新请求、幂等LRU缓存1000条。剩余方向候选少于9条预警；未知性别同时检查并集少于18条。以上仅为开发试验值，调整不改变三名/六名、真实出处和本轮不重复等硬要求。

### 11.3 内容质量验收

自动测试覆盖原句、取字关系、计数、规则和数据完整性；审核覆盖寓意、上下文与名字是否适合使用。两者不能互相替代。

模拟样本至少包含常见单姓、复姓、多音姓，以及曾发现过不良搭配的姓氏。除了平均耗时，还记录较慢请求和失败情况。
