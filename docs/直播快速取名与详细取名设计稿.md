# 直播快速取名与详细取名设计稿

状态：供审阅的实现方案，未获准实施；没有修改业务代码。

日期：2026-10-30

修订：R2，补充本轮 13 项评审涉及的设计约定。试验数值用于开发和模拟，不代表已测得的业务指标。

需求依据：[直播快速取名与详细取名需求稿](./直播快速取名与详细取名需求稿.md)

## 1. 设计结论

快速取名采用“离线准备名字资料 + 本地自动筛选 + 现有报告快照”。增加独立快速接口，不把名字库伪装成模型 Provider，不让快速流程进入模型重试逻辑。

详细取名继续使用现有 `/api/generate`、模型 Provider、完整报告页和图片接口。直播快速取名页面不再提交生日、时辰、辈分和避讳等字段。

初版基于当前本机、单 Node 服务进程和固定账号部署方式设计。使用文件保存快照、进程内缓存和串行提交，不新增数据库、任务队列或向量检索。若实际要多进程或多实例部署，文件互斥方案不成立，必须先调整存储设计，不能直接横向扩容。

本设计中的路径、类型和接口若标注“新增”，均为拟议实现，不是现有能力。尚未确定的产品参数采用明确的试验默认值，不当作用户已经确认。

## 3. 模块与流程

### 3.1 离线准备

```text
data/corpus 中的原文
    → 离线提取候选（程序或模型）
    → 自动校验 + 内容审核
    → 发布只含合格条目的版本化名字库
```

### 3.2 在线快速取名

```text
直播表单（姓氏、性别）
    → POST /api/live/quick-name
    → 登录检查、输入检查、幂等检查
    → 已加载的名字库 + 已提交的近期报告记录
    → 完整姓名检查、排序、分组选择
    → 构造 ReportDocument
    → 原子保存报告快照并更新内存记录
    → 返回完整报告
    → 页面展示 / 按需导出
```

### 3.3 详细取名

主播在现有正式取名入口填写特殊条件，继续走 `/api/generate`。本版不新建在线观众登记表或私信系统。保留一个进入详细取名页面的入口即可，不把额外字段放回直播快速表单。

### 3.4 本次必须修正的详细出处流程

基础条件检查 → 出处核验 → 只对有合格出处的候选判断数量 → 不足时沿用有限补充机会 → 新候选执行相同检查 → 仍不足则明确失败，不保存为成功报告。

候选数量和补充次数沿用现有详细路径，不增加无限重试。原文存在不等于解释正确，取字关系和含义检查不能被“原句命中”替代。不得以留空出处、现代组合义或编造引文填补数量。

本项纳入整体交付，不属于“以后再修”。必须测试全部出处失败、部分失败造成数量不足、补充后足够、补充后仍不足四种情况。快速模块单独通过不代表本需求整体完成。

## 4. 数据设计

### 4.1 精选名字资料

建议新增 `data/name-library/library.json`，以一个文件作为发布单元。运行时只读，不能通过直播请求修改。

```ts
interface NameLibrary {
  schemaVersion: 1;
  libraryVersion: string;
  entries: LibraryName[];
}

interface LibraryName {
  id: string;                  // 稳定 ID，不使用数组位置
  givenName: string;           // 两个汉字，不含姓
  genderEligibility: Array<"male" | "female">;
  givenPinyin: [string, string];
  meaning: string;
  composition: string;
  citation: {
    source: string;
    piece: string;
    quote: string;
    line: string;
    sourcePieceId: string;    // 指向发布时使用的语料记录
    extraction: {
      kind: "contiguous" | "within_sentence";
      positions: [number, number];
    };
  };
  phonology?: string;         // 只能写名字本身成立的内容
  glyph?: string;
  pitfalls?: string;
}
```

以上均为新增类型。初版只支持原句中的连续取词或同一句按原顺序取字，不做跨典籍任意拼字或大规模同音替换。后者可以留给详细模型取名，避免快速库的取字关系难以核实。

`positions` 基于去标点、空白并按既有规则统一简繁后的 Unicode 字符序列，不用 UTF-16 字节偏移；发布程序保存并检查两个位置确实对应名字用字。引用原文仍保留自然标点，不展示归一化文本。

名字本体去重：相同 `givenName` 只保留一条可用记录，多个出处不重复计数。名字库中的不同版本使用同一个稳定 ID；记录停用不能造成 ID 被另一个名字复用。

入库审核记录放在离线工作资料中，包含审核人或审核方式、时间、所用语料版本、结论。正式库只包含批准条目，避免运行时引入复杂审核状态机。若没有完成内容审核，不能发布成正式可用资料。

### 4.2 全名拼音

`givenPinyin` 来自审核过的名字资料。姓氏读音复用当前 `pinyin-pro` 姓氏模式，复姓作为整体处理；不要对姓名逐字套普通读音后覆盖已确认的名字读音。现有 `POLYPHONIC_SURNAMES` 只是提示名单，不是读音字典。

当前安装库已实际核对仇 qiú、单 shàn、解 xiè、曾 zēng、查 zhā、欧阳 ōu yáng。实施拼音模块的开发者负责把这些及实际支持范围写入回归用例；只对实测缺口增加有依据的覆盖项，不重建整本姓氏字典。库返回某个读音也不证明它覆盖全部家族读法。

建议为 `NameDetail` 增加可选 `fullPinyin?: string`、`pinyinHint?: string`：

- 快速报告写入完整拼音和提示，直播、报告、导出优先使用快照字段。
- 旧报告没有新字段，继续走原有拼音兼容逻辑。
- 现有 `pinyin` 含义仍是名字拼音，不把它偷偷改成全名拼音。
- 名字读音资料缺失的条目在发布时拦截；姓氏无法确定时在选名前返回 422 `SURNAME_PRONUNCIATION_UNRESOLVED`，不能靠换候选名字解决姓氏问题。
- 前端在姓氏输入框旁显示“这个姓氏的读音暂不能可靠确认，请核对姓氏或转详细取名”，保留输入和上一份成功结果，不跳空白错误页、不自动重试、不消费名字。已支持的常见多音姓正常取名并显示核对提示，不统一当成错误。
- 姓氏存在多个家庭读法时不承诺自动推断其家族读法；当前只支持姓名工具可可靠处理的范围。

### 4.3 快速报告元数据

沿用 `ReportDocument` 和 `NameDetail`，新增可选元数据：

```ts
quickNaming?: {
  libraryVersion: string;
  selectorVersion: string;
  rulesVersion: string;       // 禁用组合及热门字规则版本
  blocklistVersion: string;   // 提交时采用的紧急停用版本
  entryIds: string[];
  sessionId: string;
  roundId: string;
  requestId: string;
  previousReportId?: string;
  requestFingerprint: string;
};
```

- `source` 现有合法值只有 `live | formal`，快速报告仍使用 `live`，不新增未经定义的来源值。
- `providerName` 是字符串，可使用 `curated-library` 标识快速库来源；显示层不能将其描述为模型生成。
- 用 `quickNaming` 明确识别新快速报告，旧报告不自动补标记。
- 未知性别的 `overview.maleNames`、`femaleNames` 各三条；`names` 保存完整六条详情。
- 为兼容现有 `primaryName`，快速未知性别固定写 `maleNames[0]`，仅为结构兼容，不能解释为跨性别首推。直播、报告总览、名字标签、Canvas 导出、服务端图片必须按“quickNaming 存在且 gender=unknown”走两组展示，禁止显示全局首推标记；历史只显示两组摘要。各组第一项是组内展示首位。
- `request` 保持已有 `NormalizedRequest` 类型合法，固定双字、八字关闭、辈分为空、避讳为空，未知信息不用于生成推断。
- `bazi` 和 `baziFit` 不写入快速报告。
- 不编写淘汰名字、分析阶段或质量分数来填充旧报告字段。
- 快速来源说明应写明基于姓氏和性别的库内推荐，未考虑家庭避讳及生辰。

报告中的解释、出处和拼音保存完整副本。后续名字库更新不改变已交付快照。

## 5. 离线建库与发布

建议新增 `scripts/name-library/build.ts` 和 `validate.ts`，均为明确手动执行的准备工具，不由 Web 请求触发。候选生成是否批量调用模型以及费用，应另行控制，不在本设计中默认批量运行。

校验顺序：

1. 结构、字数、ID 和名字唯一性检查。
2. 书名、篇名、原句对应检查，复用现有语料能力。
3. 取字位置与名字用字检查。
4. 用字、已知禁用组合、拼音完整性检查。
5. 检查必要的审核记录和资料完整性。
6. 生成校验通过的发布库和容量摘要。

现有 `verifyCitation` 会纠正部分篇名差异，并不保证语义准确。构建程序必须让这种修正可见，完成审核后再发布；不能把纠正结果掩盖在“全通过”里。

发布采用临时文件写完、校验通过后再替换正式文件。初版在停播时发布并重启服务加载新版本，避免引入热更新、多版本并发选择等额外复杂性。旧报告仍保留旧版本内容。

### 5.1 直播期间紧急停用

完整库仍按上述流程发布；另设 `${JINYU_DATA_DIR}/name-library/disabled.json` 作为小型运行时停用文件，默认数据目录为 `data`。包含 `version`、`givenNames`（全姓氏停用某名字）、`fullNames`（只停用特定完整姓名），条目附原因。维护者编辑并原子替换，不要求主播停播或重启。

服务在每次新推荐前读取该小文件并校验，使用内容摘要识别版本，不依赖文件监听事件一定可靠。初次部署提供有效空名单；运行中格式错误或文件缺失保留上次有效版本并在状态栏报警，首次启动没有有效版本则保持未就绪。

选择后、提交前再次读取并应用最新有效名单；如果变化导致所选名字被禁用，重新选择一次，仍在持续变化则返回可重试错误，不提交失效候选。停用生效边界是提交前最后一次有效读取；已经提交的报告及其幂等重放仍保持原快照，界面另提示其名字已被停用，允许换组，不改写历史。

不新增完整管理后台。发布新库也不能清空紧急停用文件，恢复使用须显式移除对应停用项。

首批小样本只验证实现。正式库必须经过容量模拟，不能在 README 中把试验条数写成正式保证。

## 6. 自动筛选算法

新增 `src/domain/quick-naming/select.ts`，实现不依赖网络的纯选择函数。名字库、使用记录、随机种子或请求标识由调用方传入，便于确定性测试。

### 6.1 基础过滤

依次检查：

- 只接收当前正式库条目。
- 两字名、资料完整、适用方向匹配。
- 排除 `src/config/l1-templates.json` 中按 `givenName` 精确匹配的禁用名字组合，与姓无关。
- 新增已确认不良全名表，按 `surname + givenName` 精确匹配，作用仅于该完整姓名；与上述名字组合表不是同一范围。
- 应用 §5.1 的运行时停用覆盖。两个范围的条目不能混在一张没有范围说明的字符串表里。
- 排除本轮已经展示过的 `givenName`，不是只排除库 ID。
- 生成并确认全名拼音。

不把“姓氏和名字有同一个字”“声调相同”“一个字偏热门”等直接作为一律淘汰的理由。模糊谐音匹配先作为审核线索，不无限扩大黑名单。

初版不构建完整汉语语义或方言检测器。规则只承诺检查已维护的明确问题；对当前没有证据的问题不杜撰算法能力。

### 6.2 排序

采用可解释的排序项，不设计姓名百分制。建议试验顺序为：

1. 同姓近期推荐次数较少；
2. 同场直播推荐次数较少；
3. 热门用字数量较少；
4. 同等条件下按请求种子稳定轮换。

删除未定义的“使用风险较少”排序项。明确不能接受的问题由基础过滤处理，其他提醒展示给用户，不从 `pitfalls` 的长度或措辞推导分数。热门用字数量按名字的 Unicode 字符命中 `src/config/l2-chars.json` 的数量计算，在加载时派生，不在 LibraryName 中重复存储字段。该名单和禁用组合随 `rulesVersion` 固定，更新规则后重启预热；紧急停用单独处理。

同姓近期窗口建议先以最近七天做试验常量，单独集中定义，注明未确认；不新增面向主播的配置面板。实际窗口通过模拟和直播数据确定。

稳定轮换使用 `requestId + entryId + selectorVersion` 的稳定散列作为末级排序项。相同请求重试返回原快照，不重新抽签；新请求只在合格候选中改变同级顺序。

### 6.3 已知性别选择

从合格候选中选三个。第一遍优先挑用字不重叠的名字；不足三个时，可在同一合格池中放松“组内用字不同”这个软偏好，但不能恢复本轮重复名、禁用组合或缺出处条目。

最终首位为首推，其余两位为备选。精确返回三个，不再通过现有组装器截选四个后让直播隐藏一个。

### 6.4 未知性别分组

将候选分为仅男向、仅女向、两边均可。必须选出男向三名、女向三名，且六名互不重复。

不能先随意给男向挑三个，再用剩余候选给女向，这可能把女向必须使用的中性候选提前占用。

实现一个仅六个位置的可行性选择：优先处理可用余量较小的一组；每次暂选一个名字后，检查剩余池是否仍满足：

- 剩余男向可用数不少于男向空位；
- 剩余女向可用数不少于女向空位；
- 剩余候选并集不少于全部空位。

不满足就跳过当前候选，继续尝试；两方向共享候选不能重复分配。组内用字差异是软偏好，先保证数量、方向和唯一性。固定六个位置，不做面向任意分组的通用优化框架。

无可行结果返回不足错误，不用三条重复拼成六条。

### 6.5 库容量评估

离线模拟输出每个测试姓氏的男向可用数、女向可用数、并集数量、可换组次数和重复统计。已知性别与未知性别分别模拟，不能只看库总条数。

测试场景包括常见单姓、复姓、多音姓、已有问题案例，以及同姓连续取名、频繁换组、连续未知性别。模拟中记录同场按名字用字计算的重复，也记录按完整姓名计算的重复，避免用换姓掩盖重复感。

真实语义质量由审核和样本试用判断，不能只用统计通过率证明名字好。

### 6.6 开发用固定模拟输入

以下是可复现试验值，不是人口统计或已确认直播画像。实现第一步先落成测试夹具，随机种子固定为 20261030。

| 参数 | 基线试验值 |
| --- | --- |
| 单场 | 120 分钟、100 位观众，即 100 次首次取名 |
| 性别 | 男 40 位、女 40 位、未知 20 位 |
| 换组 | 30 位各换一次，其中男 12、女 12、未知 6，共 130 次新推荐、468 个名字位置 |
| 姓氏 | 合成非均匀分布：王18%、李16%、张14%、刘12%、陈10%、杨8%、赵7%、黄6%、周5%、吴4% |
| 时间 | 首次请求在120分钟内按固定种子分布，换组至少间隔5秒；突发请求另测 |
| 历史 | 先模拟连续7场，每天1场，再评价第8场及7天窗口边界 |

该姓氏分布仅为工程构造，禁止称作人口普查分布。正式容量结论须额外使用一份带来源年份、人数或占比的公开姓氏数据或匿名实际直播分布；仅有排名时不得自行当成真实概率。准备数据夹具由容量测试实现者负责，正式容量验收前必须冻结版本。

独立压力组：同一个姓氏连续100位；20位各换5次；全部未知性别；复姓与多音姓定向样本；同账号快速连点30次。质量、容量测试与限流测试分开，不能用限流拒绝掩盖库容量不足。报告每个场景结果，不用混合平均值盖住失败。

## 7. 快速接口

新增 `POST /api/live/quick-name`，沿用现有登录检查，普通 JSON 响应，不使用 SSE。

```json
{
  "surname": "高",
  "gender": "unknown",
  "sessionId": "客户端生成的合法随机标识",
  "roundId": "本轮随机标识",
  "requestId": "本次点击随机标识",
  "previousReportId": "仅换一组时携带"
}
```

- 服务端严格校验长度、格式、姓氏和性别；标识不直接用于文件路径。
- 不接收生日、辈分、避讳等额外条件，避免客户端残留被静默使用。
- 同一轮锁定姓氏和性别；改变条件应开始新一轮。
- 换组必须引用该轮最新报告，旧页面的过期引用返回冲突并提示刷新当前结果。
- 服务端从已保存报告恢复本轮排除集合，不相信客户端传来的“已展示名字数组”。
- 同一 `requestId` 和相同请求返回相同报告；同一 ID 配不同参数返回冲突。
- 正常成功返回 `{ ok: true, report }`，报告已保存，不额外 GET 一次才能展示。

`requestFingerprint` 使用固定顺序的 JSON 数组 `[surname.trim().normalize("NFC"), gender, sessionId, roundId, previousReportId ?? null]` 的 UTF-8 SHA-256。非法输入先拒绝，不隐式改性别或归并姓氏。requestId 是幂等键，不放进指纹；当前库版本和规则版本也不放进请求指纹，已提交请求必须先重放原快照。

### 7.1 最小限流

登录后先查已提交的幂等结果，再对新请求限流。试验默认值：固定账号每个滚动60秒最多30个新请求，同时最多一个新快速取名请求进行中；同ID的进行中重复请求合并等待，不重复排队或消费。换 roundId/sessionId 不能绕过账号限流。

超限返回429及 `Retry-After`，前端保留结果并提示稍后再试，不自动连环重试。失败的新请求也计入接口频率预算，但只有提交的报告才计入推荐使用量。上述数值为试验常量，不新增可配置后台；限流不提供跨进程保证。

建议错误分类：输入错误400、未登录401、请求或已结束会话冲突409、候选不足或姓氏读音无法确认422（必须不同错误码）、限流429、预热中或库不可用503、未提交的存储失败500。错误码如 `QUICK_POOL_INSUFFICIENT` 属于新增快速接口契约，不塞入现有枚举中未定义的值。

不足响应给主播说明哪个方向缺少可用名字，不暴露未审核候选作为临时替代。

## 8. 使用记录、幂等与保存

### 8.1 尽量不新增一份独立账本

以带 `quickNaming` 元数据的报告快照作为已交付推荐的事实来源。内存建立：请求 ID → 报告、本轮已展示集合、同姓近期计数、同场计数。

服务启动时预热正式库、有效停用名单和推荐索引，不由第一次取名请求触发。使用 Next.js 服务端启动入口 `instrumentation.ts` 的 Node 分支启动一次预热任务，并用进程级共享 Promise 避免重复执行。实际部署启动方式必须验证确实执行该入口。

新增受登录保护的 `GET /api/live/status` 返回 `warming | ready | failed`。直播页在准备中禁用取名，失败显示原因和重试准备入口。未就绪的直接取名请求返回503，不在请求中等待全量扫描。预热完成才置 ready；准备时间单独报告，不把它藏在“两秒”之外。

统计口径固定：只计带 quickNaming 的已提交快速报告，详细模型报告不计同姓近期、同场及本轮排除。共用提交队列仅用于保存正确性，不代表合并业务统计。不承诺跨快速/详细模式去重；未来若需要把详细结果计为直播已展示，另行设计明确动作，不根据生成时间猜测。

目录及缓存遵守 `JINYU_DATA_DIR` 隔离。恢复时流式读取历史文件并只保留所需的紧凑记录，不把全部报告正文留在内存。

### 8.1.1 记录保留与会话结束

- 同姓近期记录以服务端 createdAt 为准保留滚动七天，每次新提交前及每分钟清除过期项；截止时刻为 now−7天，等于截止时刻的记录过期。
- 同场计数、本轮排除只保留当前活跃会话。新增受登录保护且幂等的会话开始接口，接受 previousSessionId 与新sessionId；串行原子保存一个小型 current-session.json，匹配当前会话才切换。“新一场”结束旧会话并释放其活跃缓存，刷新不结束会话。并发旧标签页不能重新激活已结束会话。
- 会话跨进程重启可恢复，试验最长持续12小时；超时的新取名或换组返回409并提示新开一场。已提交报告仍可查看或幂等重放。会话文件只管理生命周期，名字使用量仍以报告快照恢复。
- 请求ID缓存用有界LRU（试验上限1000条），只保存请求指纹和报告ID，不保存所有正文。新快速报告ID固定为 `q_` 加 requestId 的完整 SHA-256 十六进制串；输入ID先格式和长度校验，不能作为原始路径。
- 缓存未命中时按派生报告ID直接读快照确认幂等，不扫描全历史。因此释放缓存或结束会话不使旧请求重新生成名字；旧报告命中先重放，再判断是否允许新请求。
- 本轮排除集合在同一活跃场次中保留，下一位不立即删除前一轮服务端记录；该场结束统一释放，最长12小时且受账号限流约束。不得因释放缓存恢复本轮已用候选。

以上数字为试验默认值，可在负载验证后调整；不能通过清理内存删除正式报告。历史索引的内存体积需单独测量，不能因幂等LRU有界就宣称全进程内存固定。

### 8.2 提交顺序

当前是单服务进程，快速请求的“幂等检查 → 读取记录 → 选择 → 保存 → 更新记录”及会话切换放入快速服务串行临界区；所有报告的最终写入另共用一个短存储提交队列。固定顺序为快速服务锁→存储队列，禁止反向获取或在同一非重入队列内再次排队等待。模型生成在两者之外运行，详细报告提交只进入存储队列，防止并发索引覆盖而不混入快速统计。

提交步骤：

1. 用临时文件写完整报告，原子重命名成为正式报告文件。
2. 正式快照成功落盘即为提交成功；随后更新内存使用索引。
3. 更新历史索引，失败时保留正式快照，将索引视为待重建派生数据。
4. 返回已提交的报告。

要求原子文件操作在同一磁盘目录完成。临时文件不纳入恢复扫描。无有效正式快照则不计入推荐记录。

报告快照是事实来源，历史索引不能反过来决定报告是否存在。历史索引需在启动恢复时核对并补齐缺失记录；索引写入失败后，当前进程的历史读取也应使用恢复后的内存索引或触发修复，不长期漏掉已交付结果。

客户端断线但快照已经提交，重试相同请求返回同一结果；这属于已提交但暂未被客户端看到，不能当作一次新的换组。写快照之前失败则没有推荐消费。

该设计是新增快速防重复需要的直接存储修改，涉及现有详细报告写入，必须有并发和故障测试。不能只加一个内存锁就声称跨进程安全。

## 9. 前端状态与操作

- 继续沿用输入、生成中、结果三类界面状态。
- 快速生成中只显示“正在挑选名字”，不使用模拟模型推理的百分比。
- 首次进入直播台读取服务端当前会话；没有活跃会话才请求开始。浏览器本地只是会话ID缓存，刷新恢复服务端状态，不自行创建并替换会话。
- 提供轻量的“新一场”操作，通过 §8.1.1 会话接口更换 sessionId；不接入抖音开播 API。旧标签页收到会话冲突后提示同步，不自动重开旧场次。
- “下一位”创建新的 `roundId`，清空姓氏和当前结果，性别是否保留按现有操作习惯测试后决定。
- “换一组”保留条件和 `roundId`，创建新 `requestId`，携带上一份报告 ID。
- 网络失败重试同一次操作时复用原 `requestId`；不要为重试生成新 ID。
- 保留上一份成功报告，新的请求失败不能把原结果清空。
- 按钮忙碌锁防误触，服务端幂等负责真正的重复提交控制。

本版不设计多主播同账号共享会话；多个标签页同时换组应通过最新报告引用识别冲突，不能让两个结果悄悄互相覆盖。

### 9.1 运行状态与容量提示

状态接口只向已登录操作者提供准备状态、库/规则/停用版本、停用文件错误、当前会话ID和最近错误。可按当前姓氏查询过滤后的男向数、女向数、候选并集数及扣除本轮历史后的剩余数，不加载任意未经验证的路径。

试验预警：已知方向剩余少于9条提示“可换组数量偏少”，少于3条不可组成新组；未知时任一方向少于9条或并集少于18条预警，任一方向少于3条或并集少于6条不可组成完整结果。共享中性名字分别计入方向数，但并集只算一次，不能把方向数相加当总容量。

以成功提交前后计算的容量为准，不仅显示库总条数。总体可用量不足、本轮剩余少和近期重复多分别显示，不能统称“池子耗尽”。提示放主播操作区，不遮挡给观众看的名字。

服务记录 requestId、结果码、各阶段耗时、候选数、提交状态；不记录私密详细需求。使用最近200次新请求的有界样本统计成功请求耗时P95、候选不足率和429次数，显示样本数；读音未确认422单独计数，不混入候选不足率。端到端两秒由浏览器验收，服务器P95不能冒充页面可读时间。

记录采用可轮转的结构化日志，不建设新监控平台。服务启动恢复、每次发布及当前姓氏取名时检查容量；没有真实业务分布前，不承诺能预警所有未来姓氏。

## 10. 报告和图片适配

### 10.1 快速报告构造

新增专门的 `buildQuickReport`，直接将已选三名或六名映射为现有报告结构。不要调用模型组装路径来填无意义默认文案。

资料没有读音评价、字形评价或提醒时，对应现有必填字符串写空字符串，展示层按空值隐藏。其类型仍合法，不把“没有明显硬伤”当成审核结论自动补上。

详细报告继续使用原组装流程，但必须完成 §3.4 出处过滤修正并列入测试，不顺便重写全部报告文案。

### 10.2 展示与来源

- 直播直接消费返回的 `ReportDocument`，优先使用快照中的全名拼音。
- 历史列表标明“快速推荐”与现有详细取名来源。
- 未知性别历史摘要可显示“男向三名、女向三名”，不能因现有 `slice(0, 5)` 让用户误以为只有五个。
- 旧报告没有新元数据，保持原样，不重新核验后篡改历史内容。

### 10.3 图片

已知性别复用当前首推详解、两个备选简解的排版，数据来自库内已审核资料。

未知性别暂建议一张图片分男向、女向两区，每区三名，并包含六名的拼音、简解和出处。该选择未获确认，可改为两张图；实现之前必须定下，不能直接只导出 `show.alts` 的两名。

详细取名沿用现有完整报告及图片，无需引入新的图像生成服务。快速结果页面和报告页面的图片入口都要验证六名覆盖，避免只修其中一个出口。

## 12. 测试与性能验证

### 12.1 算法测试

- 已知性别严格返回三个，未知性别两组各三个。
- 中性共享池不重复分配，覆盖“先选一组会让另一组不足”的反例。
- 字数、方向、禁用组合、取字依据、拼音缺失等无效资料被拦截。
- 换组排除整轮历史，不仅排除上一组。
- 近期计数只影响排序，不恢复禁用项；软多样性不足时仍能选满合格名字。
- 固定请求种子结果稳定，新请求能在同级候选中轮换。

### 12.2 接口与存储测试

- 未登录、非法输入、附带详细条件、请求 ID 冲突。
- 同一请求重复提交只保存一份快照、只消费一次名字。
- 两个并发请求不能读到同一旧状态并破坏同轮排除。
- 写快照失败不更新使用计数。
- 快照成功、索引写失败，重试和重启都能恢复原报告。
- 响应丢失后的重试不会换名。
- 快速与详细同时保存不丢历史条目。
- 全部存储测试使用临时 `JINYU_DATA_DIR`，不写真实直播数据。

### 12.3 展示与导出

- 男、女、未知三个完整流程以及换组耗尽。
- 复姓、多音姓和已确认名字读音。
- 快速转详细不携带过期条件，详细报告仍能读取和下载。
- 六名页面与图片都包含六个正确名字、完整拼音和对应出处。
- 库更新后打开旧报告不发生内容改变。

### 12.4 性能

记录输入提交、API 开始、库与索引就绪、筛选完成、快照提交、响应完成、姓名可读的时间。测冷启动与连续请求，报告 P50、P95、最大值及失败数，不能只测纯函数。

P95 两秒为需求稿中的建议目标，仍待确认。以 ready 后提交至名字可读为口径，首次点击也纳入，不排除慢样本；启动预热耗时另报。用实际发布库规模和历史数量测试，禁止用空历史和十条假名字宣称正式性能达标。

容量模拟至少产出：各姓各方向合格数量、连续换组能力、整场按名字和全名计算的重复率、共享中性池耗尽情况。先执行 §6.6 固定负载，再加入有来源的姓氏分布或真实直播记录；不能把后者待采集作为不运行基线模拟的理由。

### 12.5 本轮评审新增验收

- 启动预热失败/未完成时不可取名；ready后的首次点击不触发全量恢复。
- 详细报告保存不改变快速计数；重开快照和幂等重放不增加计数。
- 紧急停用修改后新请求排除目标，坏文件保留旧版本并提示；历史和重放不被改写。
- 新ID频繁请求受账号限流，换轮次不能绕过；重试相同已提交ID不重复消费。
- 热门字数量按现有名单派生，无冗余Schema；停用范围精确区分名与全名。
- 姓氏无法确认时输入和上次结果保留；曾、单、仇、解、查、欧阳有直接回归。
- 未知性别的直播、报告总览、标签、两类图片与历史均不出现误导的全局首推。
- 七天边界裁剪、会话切换、12小时超时、LRU淘汰、重启后旧请求重放不重新取名。
- 容量预警区分方向与共享并集；候选不足率不把读音错误算进去。
- 详细出处四种场景按 §3.4 通过；该项未完成时不得宣布整体验收通过。

## 13. 分步实施建议

1. **冻结试验输入并做纯算法验证**：先落地 §6.6 夹具与姓氏拼音回归；少量审核资料验证三名、六名、防重复和可行性，不作为正式直播交付。
2. **接快速 API 和快照提交**：完成启动预热、状态、幂等、限流、紧急停用、记录裁剪、重启恢复和共享存储回归。
3. **接直播 UI 与图片，修详细出处**：去额外字段、换组、容量提示、六名导出；完成 §3.4 及其四类回归。
4. **扩库并模拟真实直播**：执行固定基线和实源分布，质量、容量和速度达标后再正式启用。

任何一步不合格，修复对应问题；没有新失败证据不扩大为全项目重构。详细模型取名路径始终保留，快速模式不会自动把不足请求转成模型调用。

## 14. 待决策与限制

- 未知性别图片形式尚未确认，本文仅建议一张分组图。
- 七天窗口、12小时场次、30次/分钟、1000条LRU、容量预警及 §6.6 负载均为明确的工程试验默认值，正式运营数值由验证调整，不再留给开发任意猜测。
- 名字库审核人员、工作量、正式条数和直播容量尚未确定。
- 单进程文件存储是当前部署假设，多进程必须更换并发与提交方案。
- 人名读音与方言谐音无法通过简单算法完全判断，不能把“没有命中规则”写成“完全无风险”。
- 自动流程可快速选取已准备好的内容，但不能自动保证每条古文解释都正确；资料质量是上线前置条件。

本文给出了可实现的设计，尚未运行其中新增算法或进行性能验收。下一步应由用户审阅需求和上述待定建议，再确定实施范围。
